Absolument. Et pour ton projet, le **point 2 — Infrastructure 3D** doit être traité comme un vrai moteur à part entière. Il ne s'agit pas encore de mettre des maisons, arbres ou voitures partout : son rôle est de prendre les données propres produites par le **Road World Engine** et de les transformer en une **infrastructure 3D robuste, continue, précise et performante**.

Voici le cahier des charges que je donnerais à ton IA développeuse.

# ROAD WORLD ENGINE

## CAHIER DES CHARGES V1.1 — INFRASTRUCTURE 3D

### Statut

Phase 2 du projet Road World Engine.

### Dépendance

Cette phase dépend exclusivement du moteur logique de génération routière validé en V0.x.

### Objectif

Transformer les données géométriques et topologiques du Road World Engine en une infrastructure 3D cohérente, continue, propre, optimisée et exploitable par les futures couches du simulateur.

---

# 1. OBJECTIF GÉNÉRAL

La V1.1 doit créer la couche de représentation 3D de l'infrastructure routière.

Le système doit convertir :

* routes ;
* voies ;
* intersections ;
* ronds-points ;
* trottoirs ;
* bordures ;
* terre-pleins ;
* marquages ;

en géométrie 3D.

La logique du monde reste indépendante du rendu.

Architecture :

```text
ROAD WORLD DATA
       ↓
GEOMETRY ADAPTER
       ↓
3D INFRASTRUCTURE GENERATOR
       ↓
MESH GENERATION
       ↓
MATERIAL SYSTEM
       ↓
OPTIMIZATION
       ↓
WEBGL RENDERER
```

---

# 2. RÈGLE ABSOLUE

Le moteur 3D ne doit jamais recréer ou deviner la géométrie routière.

Il doit utiliser les données du moteur logique.

Exemple :

```text
Road ID
Road geometry
Road width
Lane data
Intersection data
Sidewalk data
```

doivent être la source permettant de construire le mesh.

Il est interdit de créer manuellement une route 3D qui ne correspond pas à la route logique.

---

La V1.1 est responsable de :

* génération de chaussées ;
* génération des voies ;
* génération des bordures ;
* génération des trottoirs ;
* génération des terre-pleins ;
* génération des intersections ;
* génération des ronds-points ;
* génération des raccordements ;
* génération des marquages routiers ;
* gestion des matériaux ;
* génération des surfaces ;
* gestion des normales ;
* gestion des UV ;
* collisions de base ;
* optimisation du rendu ;
* streaming éventuel ;
* debug visuel.

---

# 4. CE QUI N'EST PAS ENCORE DANS CETTE VERSION

Ne pas implémenter :

* maisons détaillées ;
* bâtiments détaillés ;
* voitures ;
* trafic IA ;
* piétons ;
* végétation avancée ;
* décoration urbaine ;

* scoring.

Les panneaux et feux peuvent être représentés temporairement par des placeholders uniquement si cela est nécessaire pour tester les connexions.

# 6. ROAD MESH GENERATOR

Le générateur doit transformer une route logique en chaussée 3D.

Entrées :

```text
Road
├── centerline
├── width
├── lanes
├── elevation
├── banking
├── roadType
└── boundaries
```

Sorties :

```text
RoadMesh
├── geometry
├── material
├── UV
├── normals
├── collision
└── metadata
```

---

# 7. CENTERLINE

La géométrie doit être construite autour de la centerline logique.

Le système doit pouvoir gérer :

* lignes droites ;
* courbes ;
* courbes composées ;
* virages serrés ;
* longues courbes ;
* transitions.

La géométrie doit suivre précisément la centerline.

---

# 8. LARGEUR

La largeur de la route doit être paramétrique.

Exemple :

```text
Road width = 7 m
```

ou :

```text
2 lanes × 3.5 m
```

Le mesh doit être recalculé automatiquement lorsque la largeur change.

Aucune largeur ne doit être hardcodée dans le générateur.

---

# 9. NOMBRE DE VOIES

Une route peut avoir :

```text
1 lane
2 lanes
3 lanes
4 lanes
6 lanes
...
```

Le générateur doit calculer automatiquement :

* largeur totale ;
* séparation des voies ;
* limites ;
* position des marquages.

---

# 10. PROFIL DE ROUTE

Prévoir un système permettant de définir :

```text
RoadProfile
├── laneWidth
├── shoulderWidth
├── sidewalkWidth
├── curbHeight
├── roadThickness
└── medianWidth
```

Les profils doivent être configurables.

---

# 11. CHAUSSÉE

La chaussée doit être une surface continue.

Elle ne doit pas présenter :

* trous ;
* fissures géométriques ;
* triangles retournés ;
* chevauchements ;
* espaces entre segments.

---

# 12. SEGMENTATION

Une longue route ne doit pas nécessairement être un mesh gigantesque.

Le système doit pouvoir diviser les routes en segments.

```text
Road
├── Segment 01
├── Segment 02
├── Segment 03
├── Segment 04
└── ...
```

Cette segmentation servira ensuite :

* au streaming ;
* au LOD ;
* à l'optimisation ;
* aux modifications locales.

---

# 13. CONTINUITÉ ENTRE SEGMENTS

Les segments doivent être parfaitement raccordés.

Il ne doit jamais y avoir :

```text
SEGMENT A
──────────

        GAP

──────────
SEGMENT B
```

ni :

```text
SEGMENT A
──────────
        /
       /
SEGMENT B
```

Les transitions doivent être continues.

---

# 14. INTERSECTIONS

Les intersections doivent être générées à partir de l'Intersection Engine.

L'Infrastructure Engine ne doit pas simplement superposer deux routes.

Il doit construire une surface d'intersection cohérente.

Exemple :

```text
──────────────
      │
      │
      │
```

La zone centrale doit être une vraie géométrie permettant :

* circulation ;
* changement de voie ;
* virage ;
* marquage ;
* futur trafic.

---

# 15. INTERSECTION EN T

Le générateur doit produire :

* chaussée ;
* raccordement ;
* bordures ;
* trottoirs ;
* transitions.

---

# 16. CARREFOUR EN X

Même principe.

Les quatre branches doivent être raccordées géométriquement.

Les surfaces ne doivent pas se superposer de manière visible.

---

# 17. INTERSECTION COMPLEXE

Le système doit accepter plus de quatre branches.

Exemple :

```text
       │
       │
───────┼───────
      / \
     /   \
```

La géométrie doit être calculée dynamiquement.

---

# 18. ROND-POINT

Créer un générateur spécialisé.

Le rond-point doit comprendre :

```text
Roundabout
├── central island
├── circulating road
├── entrances
├── exits
├── lane geometry
├── curbs
└── sidewalks
```

L'anneau doit être parfaitement fermé.

---

# 19. BORDURES

Les bordures doivent être générées automatiquement à partir des limites de chaussée.

Paramètres :

```text
height
width
profile
material
```

Les bordures doivent suivre les courbes de la route.

---

# 20. TROTTOIRS

Les trottoirs doivent être dérivés des limites routières.

Architecture :

```text
Road boundary
      ↓
Sidewalk generator
      ↓
Sidewalk mesh
```

Ils doivent suivre :

* lignes droites ;
* courbes ;
* intersections ;
* ronds-points.

---

# 21. TROTTOIRS AUX INTERSECTIONS

Les trottoirs doivent être correctement raccordés autour des intersections.

Pas de :

* trous ;
* chevauchements ;
* triangles étranges ;
* murs verticaux ;
* surfaces flottantes.

---

# 22. RAMPES

Prévoir la possibilité de générer ultérieurement :

* rampes PMR ;
* abaissements de trottoirs ;
* transitions.

Pour V1.1, l'architecture doit être préparée même si tous les profils ne sont pas encore implémentés.

---

# 23. TERRE-PLEIN CENTRAL

Supporter :

```text
Median
├── width
├── curb
├── surface
└── optional vegetation
```

La végétation n'est pas obligatoire en V1.1.

---

# 24. MARQUAGES ROUTIERS

Créer un générateur procédural de marquages.

Supporter :

* lignes continues ;
* lignes discontinues ;
* lignes centrales ;
* lignes de voie ;
* lignes d'arrêt ;
* flèches ;
* zébras ;
* passages piétons basiques.

---

# 25. MARQUAGES PARAMÉTRIQUES

Les marquages ne doivent pas être des images arbitrairement posées.

Ils doivent suivre la géométrie.

Exemple :

```text
Lane centerline
      ↓
Marking Generator
      ↓
Procedural geometry
```

Ainsi une ligne doit automatiquement suivre une route courbe.

---

# 26. LIGNES DISCONTINUES

Paramètres :

```text
lineLength
gapLength
lineWidth
```

Le générateur doit suivre la longueur réelle de la route.

---

# 27. LIGNES D'ARRÊT

Les lignes d'arrêt doivent être générées à partir de la position logique fournie par l'Intersection Engine.

Elles ne doivent pas être positionnées manuellement.

---

# 28. PASSAGES PIÉTONS

Le générateur doit pouvoir transformer une définition logique :

```text
Crosswalk
position
orientation
width
length
```

en géométrie 3D.

Le passage doit être aligné avec :

* route ;
* trottoir ;
* future signalisation.

---

# 29. MATÉRIAUX

Créer un MaterialManager centralisé.

Prévoir au minimum :

```text
Road asphalt
Sidewalk
Curb
Road marking
Concrete
Median
```

Les matériaux doivent être configurables.

---

# 30. MATÉRIAUX PROCÉDURAUX

Éviter autant que possible de créer une texture gigantesque pour chaque route.

Prévoir :

* UV répétables ;
* textures tilables ;
* éventuellement shaders procéduraux.

---

# 31. UV

Les UV doivent suivre la longueur de la route.

Une texture doit pouvoir être répétée sans étirement excessif.

Sur une route longue :

```text
texture → texture → texture → texture
```

et non :

```text
texture extrêmement étirée
```

---

# 32. NORMALES

Les normales doivent être recalculées correctement.

Objectif :

* éclairage cohérent ;
* surfaces sans artefacts ;
* courbes propres ;
* bordures correctement éclairées.

---

# 33. COLLISIONS

Créer une couche de collision adaptée au futur véhicule.

Les collisions doivent suivre :

* chaussée ;
* bordures ;
* trottoirs ;
* obstacles structuraux.

Pour V1.1, privilégier la simplicité et les performances.

---

# 34. COLLISION DATA

Les données de collision doivent être séparées des meshes visuels lorsque cela est utile.

Architecture :

```text
Visual Mesh
Collision Mesh
Logical Geometry
```

Ces trois niveaux peuvent être différents.

# 35. TERRAIN

Le moteur doit prévoir :

```text

        ↓
Road elevation
        ↓
Road mesh
```

Il doit être possible d'ajuster les routes au terrain.

---

# 36. ROUTES EN PENTE

Prévoir :

* montée ;
* descente ;
* changement progressif d'altitude.

# 37. DÉVERS

```text

```

---

# 38. Z-FIGHTING

Le moteur doit empêcher les surfaces quasiment coplanaires de se superposer inutilement.

Cela concerne notamment :

* route ;
* marquage ;
* trottoir ;
* bordure.

---

# 39. MESH OPTIMIZATION

Le système doit éviter de créer :

* un mesh par petit objet inutilement ;
* des milliers de draw calls ;
* des géométries identiques dupliquées.

Prévoir :

* batching ;
* instancing ;
* fusion de meshes lorsque pertinent ;
* géométrie partagée.

---

# 40. CHUNKING

Le monde doit être découpable en chunks.

Exemple :

```text
World
├── Chunk 0,0
├── Chunk 0,1
├── Chunk 1,0
├── Chunk 1,1
└── ...
```

Une route traversant plusieurs chunks doit rester continue logiquement.

---

# 41. LOD

Prévoir au minimum :

```text
LOD0 = proche
LOD1 = moyen
LOD2 = éloigné
```

Les routes éloignées peuvent utiliser une géométrie simplifiée.

---

# 42. FRUSTUM CULLING

Les éléments hors champ ne doivent pas être rendus lorsque cela est possible.

---

# 43. STREAMING

L'architecture doit permettre ultérieurement :

```text

Load
      ↓
```

# 73. RÈGLE FINALE POUR L'IA DÉVELOPPEUSE

Ne jamais résoudre un problème géométrique avec une position hardcodée lorsque le problème peut être résolu par un calcul.

Ne jamais masquer une erreur géométrique avec un mesh décoratif.

Ne jamais ajouter un offset arbitraire uniquement pour corriger un cas particulier sans comprendre pourquoi la géométrie est incorrecte.

Toute correction doit être faite dans l'algorithme responsable de la génération.

Le résultat recherché n'est pas une scène 3D qui fonctionne dans un seul exemple.

Le résultat recherché est un **système capable de générer correctement des milliers de configurations différentes**.
