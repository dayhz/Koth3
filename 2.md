# CAHIER DES CHARGES — ROAD WORLD ENGINE

## Moteur procédural de génération de quartiers urbains réalistes pour simulateur auto-école

### Version 1.0 — Fondation du projet

---

# 1. VISION DU PROJET

Le projet consiste à développer un **moteur de génération, de construction, de validation et de rendu d'environnements routiers urbains réalistes**, destiné à servir de fondation au futur simulateur de conduite auto-école.

Le moteur ne doit **pas être conçu comme une simple scène 3D**.

Il doit comprendre la ville comme un ensemble de systèmes interdépendants :

```text
VILLE
 │
 ├── Terrain
 │
 ├── Réseau routier
 │    ├── Routes
 │    ├── Voies
 │    ├── Intersections
 │    ├── Ronds-points
 │    └── Connexions
 │
 ├── Infrastructure piétonne
 │    ├── Trottoirs
 │    ├── Passages piétons
 │    └── Traversées
 │
 ├── Réglementation
 │    ├── Panneaux
 │    ├── Feux
 │    ├── Marquages
 │    └── Priorités
 │
 ├── Urbanisme
 │    ├── Quartiers
 │    ├── Îlots
 │    ├── Parcelles
 │    └── Zones
 │
 ├── Bâtiments
 │    ├── Maisons
 │    ├── Immeubles
 │    ├── Commerces
 │    ├── Écoles
 │    └── Services
 │
 ├── Mobilier urbain
 │
 └── Validation
```

Le futur simulateur de conduite sera **une couche supérieure** utilisant ce moteur.

---

# 2. OBJECTIF PRINCIPAL

Le moteur doit pouvoir générer automatiquement un quartier urbain cohérent à partir de paramètres.

Exemple :

```text
Générer un quartier résidentiel
Dimensions : 1000m × 1000m
Densité : moyenne
Routes principales : 50 km/h
Routes résidentielles : 30 km/h
Circulation : droite
Nombre d'écoles : 2
Commerces : faible
Intersections à feux : 4
Ronds-points : 2
Stationnement : modéré
```

Le moteur doit alors construire :

1. le réseau routier ;
2. les intersections ;
3. les voies ;
4. les trottoirs ;
5. les îlots ;
6. les parcelles ;
7. les bâtiments ;
8. les accès ;
9. les passages piétons ;
10. les panneaux ;
11. les feux ;
12. les marquages ;
13. le mobilier urbain ;
14. les zones de stationnement.

**Aucun élément ne doit être placé arbitrairement.**

# 3. PRINCIPE ABSOLU DU PROJET

## L'IA développeuse ne doit jamais corriger manuellement les symptômes.

Le moteur doit être conçu pour empêcher les erreurs à la source.

### Mauvaise architecture

```text
Créer route
Créer maison
Créer panneau
Créer feu
Créer trottoir
→ essayer de les aligner
```

### Architecture demandée

```text
Créer réseau routier
        ↓
Créer intersections
        ↓
Calculer voies
        ↓
Calculer îlots urbains
        ↓
Calculer parcelles
        ↓
Calculer bâtiments
        ↓
Calculer réglementation
        ↓
Calculer signalisation
        ↓
Calculer passages piétons
        ↓
Calculer mobilier
        ↓
VALIDER L'ENSEMBLE
        ↓
RENDER
```

# 4. LE MOTEUR DOIT ÊTRE DATA-DRIVEN

Les objets ne doivent pas uniquement être des meshes 3D.

Un objet routier doit posséder une représentation logique.

Exemple :

```text
Road
{
    id
    geometry
    width
    lanes
    direction
    speedLimit
    roadType
    connectedNodes
    sidewalks
    markings
    signs
    intersections
}
```

La représentation logique est la **source de vérité**.

Le modèle 3D n'est que sa représentation visuelle.

# 6. ROAD NETWORK ENGINE

C'est le cœur du moteur.

Il doit gérer un véritable **graphe routier**.

```text
Node
  │
  ├── Road
  │
  ├── Road
  │
  └── Road
```

Chaque route doit être définie par :

* point de départ ;
* point d'arrivée ;
* courbe ;
* largeur ;
* nombre de voies ;
* sens ;
* type ;
* vitesse ;
* connexions ;
* trottoirs ;
* marquages ;
* règles.

---

# 7. TYPES DE ROUTES

Le moteur doit disposer au minimum de :

### Route résidentielle

* 20–30 km/h ;
* faible trafic ;
* 1 ou 2 voies ;
* maisons proches ;
* stationnement possible.

### Route secondaire

* 30–50 km/h ;
* trafic moyen ;
* plusieurs connexions.

### Route principale

* 50 km/h ou plus selon configuration ;
* plusieurs voies ;
* intersections importantes ;
* feux possibles.

### Avenue

* largeur importante ;
* plusieurs voies ;
* terre-plein éventuellement ;
* trottoirs ;
* mobilier urbain.

### Rue étroite

* largeur réduite ;
* circulation faible ;
* environnement résidentiel.

### Impasse

* aucun débouché traversant ;
* possibilité de zone de retournement.

### Route commerciale

* commerces ;
* stationnement ;
* accès véhicules ;
* passages piétons fréquents.

### Zone scolaire

* vitesse réduite ;
* signalisation spécifique ;
* passages piétons ;
* trottoirs renforcés.

---

# 8. GÉOMÉTRIE DES ROUTES

Le moteur doit utiliser des géométries cohérentes.

Les routes doivent pouvoir être :

* droites ;
* courbes ;
* en S ;
* en arc ;
* raccordées tangentiellement ;
* raccordées à des intersections.

### Interdiction

Aucune route ne doit se terminer :

* dans une autre route sans intersection ;
* dans un bâtiment ;
* dans un trottoir ;
* dans une parcelle ;
* dans le vide.

Chaque extrémité doit être :

```text
CONNECTED
```

ou

```text
VALID TERMINATION
```

---

# 9. RACCORDEMENT DES ROUTES

C'est une fonctionnalité critique.

Lorsqu'une route rejoint une autre :

```text
Road A
───────────────┐
               │
               │ Road B
               │
```

le moteur doit automatiquement :

1. calculer le point de connexion ;
2. créer l'intersection ;
3. recalculer la géométrie ;
4. connecter les voies ;
5. connecter les trottoirs ;
6. recalculer les marquages ;
7. recalculer les règles ;
8. recalculer les panneaux ;
9. recalculer les passages piétons.

# 10. INTERSECTION ENGINE

Types obligatoires :

### Intersection en T

```text
───────┬───────
       │
       │
```

### Intersection en X

```text
\     /
 \   /
  \ /
  / \
 /   \
/     \
```

### Carrefour complexe

Plus de quatre branches.

### Rond-point

Le moteur doit comprendre :

* anneau ;
* entrées ;
* sorties ;
* voies ;
* priorité ;
* îlot central ;
* passages piétons.

### Intersection à feux

Elle doit comprendre :

* groupes de feux ;
* voies contrôlées ;
* lignes d'arrêt ;
* phases ;
* traversées piétonnes.

# 11. LANE ENGINE

Chaque voie doit être une entité logique.

Elle doit connaître :

```text
Lane
├── id
├── parentRoad
├── direction
├── width
├── startNode
├── endNode
├── allowedMovements
│   ├── straight
│   ├── left
│   └── right
└── speedLimit
```

Cela permettra ensuite aux véhicules IA de réellement comprendre le réseau.

# 14. URBAN BLOCK ENGINE

# 29. PROCÉDURALITÉ

Le générateur doit utiliser une **seed**.

Exemple :

```text
Seed: 482915
```

La même seed doit produire exactement le même quartier.

Changer la seed doit générer une nouvelle variation.

Cela permet :

* reproduction des bugs ;
* partage de cartes ;
* tests ;
* génération infinie.

---

# 50. RÈGLE D'OR DU PROJET

> **Chaque objet doit avoir une raison d'exister et une relation logique avec son environnement.**

Une maison existe parce qu'une parcelle existe.

Une parcelle existe parce qu'un îlot existe.

Un îlot existe parce que les routes l'ont créé.

Un panneau existe parce qu'une règle existe.

Un feu existe parce qu'une intersection le nécessite.

Un passage piéton existe parce qu'une traversée est nécessaire.

Un trottoir existe parce qu'une route existe.

C'est cette philosophie qui doit guider **toute l'architecture**.

# 60. CONDITION DE RÉUSSITE DU PROJET

Le projet ne sera pas considéré comme réussi parce qu'il produit « une jolie carte ».

Il sera réussi lorsque le moteur sera capable de répondre **logiquement** à des questions comme :

> Quelle route mène à cette intersection ?

> Quelle voie contrôle ce feu ?

> Quel véhicule a la priorité ?

> Pourquoi ce panneau STOP se trouve-t-il ici ?

> Quelle parcelle appartient à cette maison ?

> Comment accéder à cette maison depuis la route ?

> Quel passage piéton dessert cette école ?

> Quelles routes sont connectées à cette avenue ?

> Où peut-on placer légalement un panneau ?

> Cette intersection est-elle valide ?

> Ce quartier est-il entièrement connecté ?

Si le moteur peut répondre à ces questions, **alors nous aurons réellement construit la fondation du simulateur.**
